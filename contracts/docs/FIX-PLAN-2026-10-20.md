# GooseExecutor next deploy: the fix plan (2026-10-20)

Fixes for the review findings Adrian accepted (REVIEW-2026-10-20-adversarial.md; JUSTALAB-DECISIONS.md, "The executor review's 14 findings: all takes agreed"). Written by a Claude workflow on 2026-10-20: two fact-finders (Aave V4's verified Spoke; the B20 stock tokens and Aave V3 USDC), four designers, and one integrator who merged the four designs and compiled them together.

**Status:**
- **Draft code:** all four designs are merged on local branch `jl/executor-fixes` (4e780f7, on top of this branch) and build. Measured with `forge build --sizes`: GooseExecutor is **24,170 B** (406 B headroom), SellJob 20,259 B, ProtectJob 9,717 B, SaveJob 8,569 B. The draft isn't reviewed yet, and the unit tests don't compile against it until the signature updates in section 3 are made. Fork tests haven't been run.
- **Facts that settle earlier open questions:**
  - **H6 is real.** It's confirmed in Aave V4's verified Spoke: withdraw moves the position to the latest config, while repay and `getUserAccountData` use the stored one.
  - **The B20 stock tokens behave cleanly.** No fee, no rebase, no hooks, and the multiplier is display-only, so the exact-balance post-checks are sound.
  - **Still open:** the V4 Hub implementation (`0xF912…D2F6`) isn't verified on Sourcify. Step 0a matches its bytecode.
- **Effort:** about 45–50 h of focused work. With three code streams and the app side in parallel, that's about 2.5–3 working days to "ready to broadcast".

## Open questions for Adrian (product only)

1. **Remove "Stuck" (H2).** On the new executor, a failed run backs off 10, then 20, then 40 minutes and keeps trying. No agent, Protect included, switches itself off after failures any more; only a dead permission does. **Recommended: yes.** Keeping Stuck for Save, Rebalance and Entry would cost +268 B, which doesn't fit.
2. **Three departures from the triage, all recommended:**
   - **M3:** keep the swap price limit at 0 and stop runner sandwiches with a 1% band read in the same transaction. A limit at the floor can stop Protect selling in a thin, crashing pool.
   - **H4:** refuse 7702 accounts at registration (the allow-list holds only JAW's clone, and 23-byte code is refused) instead of re-checking code on every run. JAW's clone can't change its code.
   - **L4:** no tolerance for a grant that starts in the future, because the app takes the start from chain time.
3. **Wallet cash when only Protect · sell is on.** With Protect from savings off and only Protect · sell on, should wallet cash above the keep-back pay down the credit before any stock is sold? D15 suggests yes, but it changes what the sale-only setting does. It's not in this deploy unless Adrian says so.

## 1. Conflicts and overlaps: one resolution each

| # | Where | Clash | Resolution | Why |
|---|---|---|---|---|
| C1 | `SaleSkipped` event | H5 wants `(account, uint32 retryAt)`; H6-try wants `(account, bytes4 reason)` | **`SaleSkipped(address indexed account, bytes4 reason, uint32 retryAt)`** | One event, one emit site, and the app gets both the cause and the time. |
| C2 | Where a skipped sale is emitted | H5 emits it in `run`; H6-try emits it in `_sell` | **Emit only in a new `SellJob._wait(waits, account, done, why)`**, called from `run`. `_sell` returns the selector in its `hfAfter` slot on a skip. | Measured: every other layout hit "stack too deep" under via-IR. |
| C3 | `_sell` stack and bytes | H6-try passed the whole `Before` struct to `settle` | **`settle(e, account, batch, sold, hf, targetHf)` takes its own `snapshot` first. `ProtectSold` is emitted in `run`**, which already re-sums `sold`; it now also sums `repay`. | This fixed the stack error, avoids ABI-encoding `Before`, and the snapshot still comes before the batch. |
| C4 | H3 variant: two sub-calls (+186 B) or one (+33 B) | The designers left the pick open | **Two sub-calls** | **Gas:** after a 0.5M repay inside one 4.6M sub-call, a cold seven-stock sale defers, so dust re-fed every round still holds the heaviest sales back (H3's own attack). **Robustness:** a revert outside `settle` (a plan read, the bookkeeping after it) can't undo the repay. **Budget:** it fits (406 B measured). |
| C5 | Failure policy (H1 try, H2 no Stuck, H6-try) | Three partial policies | **One rule.** A revert inside a job's batch or its post-check frame is a **skip**, with that job's own wait. Only a revert outside one counts as a failure: a 10/20/40-minute cooldown, capped, and **nothing switches off except a dead permission**. | All three designers converged on this. H2's −239 B pays for the rest. |
| C6 | **Gap found:** no wait on a refused repay | H1 asked whether a ≤1M-gas retry every run was OK; H2 removes the cooldown that bounded it | **Add a repay wait** in a third lane of the per-account word: bits 168–207, the same 2/4/8/16-minute doubling as the sale. While it waits, Protect plans `None`, so planOf and the run go straight to Protect · sell. | Without it, a reverting repay would burn up to ACCOUNT_GAS for each of the 8 accounts in every perform, every block, with no backoff. The trigger can be the hub-level spoke `halted` switch (which no plan reads), a Circle blacklist, or a V3 race. Cost: +16 B core, about +250 B ProtectJob (estimate, not built). |
| C7 | H4 check vs H6's assumption | H6's note says "backing fell by exactly sold"; H4 built a lower bound | **Lower bound: `left + sold[r] <= backing[r]`** | V4 burns ceil(a/p) shares, so an honest withdrawal always drops by at least a. That proves a withdrawal ran, which is what H6 needs (Aave's after-reading is on the latest keys). An upper bound could falsely revert. |
| C8 | Pool-window charge (H4's measured drop vs M1's `sold`) | Two sources | **Charge from `sold`**, both the stock's window and the account's share | The check above proves the measured drop ≥ sold; the excess is ≤ 2 raw units. |
| C9 | M3 swap price limit | Triage says set it at the floor; the M3 designer says keep 0 | **Keep `sqrtPriceLimitX96 = 0`, and read the 1% band from slot0 in the same transaction** (Adrian to confirm, Q2) | The in-transaction band already closes M3. A floor limit turns a thin crash pool's partial fill into StockMoved, then a skip every round, so Protect stalls. If it is kept anyway, it is safe only with H6-try (now present), at about +300 B SellJob. |
| C10 | H5 wait vs H6-try | Two skip sources | **The same `!done` branch**, so post-check failures get the 2/4/8/16-minute wait | The 16-minute cap meets H6-try's "≤ 20 min" ceiling. |
| C11 | H3 loop termination | `do … while (saleOnly)` relies on ProtectSell never returning 2 | **`runAccount` returns 2 only when `!saleOnly`** (about +10 B) | A future bug can't loop until the gas floor and skip the rest of the perform. |
| C12 | `entryWaits` now holds three lanes | Name | **Rename it to `waits`.** Lanes: bits 0–127 Entry, 128–167 sale, 168–207 repay. | Zero bytes. The ABI is regenerated anyway, and the app reads `entryWaits` nowhere. |
| C13 | L1 and L4 | L1 is only safe if no stored start is in the future | **Same commit** | As both designers said. |
| C14 | M2 and H3, M2 and H2 | Sale sizing; the keep-back | **No change needed.** The sale plans after the repay (sub-call B). Save and Protect both keep `keepBack`. | — |
| C15 | H1's open question: does V4 repay refresh the config? | — | **Answered: no** (V4 facts Q4). Protect's Overshoot check stays outside a try. | Protect's before and after readings are both on the stored config. |
